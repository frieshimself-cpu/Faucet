Buyback and burn

An engine for Robinhood on Pons, on Robinhood Chain. It takes the creator rewards Pons pays the dev wallet, spends every basis point of them buying the token on the DEX, and has the swap deliver the tokens straight to the burn address.

Two things live in the repository. engine/ is the engine: TypeScript, one runtime dependency (ethers, for signing), and a test suite that runs it against an in-memory chain. site/ is this website: a static directory with no build step, rendering the ledger the engine writes.

Two invariants are enforced in code rather than promised in copy. assertPolicyBalanced() throws unless the routing policy allocates exactly 10,000 basis points, and it runs on import. After every swap the engine checks the wallet moved by exactly the amount sent plus the gas paid, and refuses to record the cycle otherwise.

The cycle

Pons creator rewards (ETH) ─→ dev wallet
                                  │
                                  ├─ keep the gas reserve
                                  └─ spend the rest ─→ router.swapExactETHForTokens(
                                                         amountOutMin = quote × (1 − 3%),
                                                         path = [WETH, ROBIN],
                                                         to   = 0x000…dEaD )
                                                       ─→ receipt: Transfer(ROBIN → 0x…dEaD)
                                                       ─→ balance check, to the wei
                                                       ─→ ledger entry

plan reads the wallet, subtracts the gas reserve, runs the remainder through the routing policy (one bucket, but the same code path a multi-bucket policy would use), quotes the router, and derives the minimum output. Nothing is signed. execute takes a plan and sends exactly that. A dry run and a live run compute the same plan; the only difference is whether execute is called.

Quiet cycles

If the spendable amount is under the minimum buyback (0.005 ETH by default), nothing is bought. Spending most of a small reward on gas would be worse than waiting, so the balance stays and the next cycle sees it.

The swap

One call on a UniswapV2Router02-compatible router: swapExactETHForTokensSupportingFeeOnTransferTokens(amountOutMin, [WETH, token], burnAddress, deadline) with the ETH as the transaction value. The recipient is the burn address, so the tokens go from the pool to 0x…dEaD inside the same transaction and never sit in the dev wallet.

  • Slippage. The engine quotes getAmountsOut first and sets amountOutMin to the quote less the configured bound (3%). Below that the router reverts, which costs gas and nothing else. A swap with no minimum is an invitation to be sandwiched.
  • Deadline. A signed swap not mined within 180 seconds is void.
  • Fee-on-transfer safe. The SupportingFeeOnTransferTokens variant is used so a token that taxes transfers still settles correctly.
  • Reading the burn. The engine parses the receipt's Transfer logs for the token and sums the amounts whose recipient is the burn address. That, not the quote, is what the ledger records as burned.

Conservation

Before recording a cycle the engine checks, in wei:

balance_before − eth_spent − gas_cost == balance_after
tokens_burned ≥ amountOutMin
gas_cost ≤ gas_reserve

If any of those fails, the cycle is not recorded and the error names the numbers. The ledger loader re-checks the first line on every receipt it reads, so a hand-edited ledger is rejected too.

Configuration

Limits live in engine/src/config.ts; chain and contract addresses come from the environment, so no address is ever a literal in the code. The site reads a generated copy, so the numbers on the page cannot drift from what the engine settles with.

FAUCET_CHAIN_ID—Pinned; the engine refuses an RPC that reports a different id.

FAUCET_DEV_WALLET_KEY—Private key. Needed only for burn --execute. Never committed.

CLI

faucet policy                       show the routing policy and prove it sums to 100%
faucet plan [--mock]                read the wallet and quote the buyback (no spend)
faucet burn [--execute] [--mock]    run a cycle; --execute sends the swap
            [--rounds N] [--write-site]
faucet status                       totals from the burn ledger
faucet verify <txhash>              confirm a tx burned the token
faucet doctor                       check config, RPC and signer

--mock runs against an in-memory chain with deterministic rewards; it is what the test suite and the pre-launch site data use. --execute is the only flag that spends anything, and only with a signer that matches the configured dev wallet.

Going live

  1. Fill .env from .env.example with the Robinhood Chain RPC, chain id and explorer prefix, the router and WETH, the token, and the dev wallet.
  2. npm run doctor. Every check must pass: it verifies the RPC reports the pinned chain id, reads the wallet balance and the token supply, and gets a quote from the router.
  3. npm run plan to see what one cycle would do, with nothing sent.
  4. Export FAUCET_DEV_WALLET_KEY in the shell that runs the cycle, never in a file, then node dist/src/cli.js burn --execute --write-site.
  5. Commit and push the updated ledger; the site redeploys with the new burn.

The engine will not send if the signer derived from the key is not the configured dev wallet, if the swap recipient is not the burn address, or if the plan does not account for the whole balance. Those checks run before the transaction is built.

Runbook

Reading a receipt

spent is the ETH sent as the swap value. burned is the token amount that reached the burn address, read from the receipt, with the quote and realised slippage beside it. wallet shows before and after, and conserved is the wei check.

When a swap reverts

error swap 0x… reverted (slippage over 300 bps, or the deadline passed). Only gas was spent.

The ETH is still in the wallet. Do not loosen the bound to force it through; run plan again and see whether the pool has settled. If reverts repeat at 3% the pool is too thin for the size, and the right fix is smaller, more frequent cycles.

When conservation fails

The cycle is not recorded. Nothing further will be sent until the numbers are explained. A mismatch usually means something else moved ETH in the wallet between the plan and the receipt; the receipt's own numbers will show which.

Scheduling

Cycles are idempotent with respect to the wallet: a run that finds nothing above the floor does nothing. Any scheduler that can run burn --execute with the key in its environment will do; hourly is a sensible starting cadence once rewards flow.

The site

Static files. It reads data/faucet.json, the ledger summary written by burn --write-site; data/burns.json, the full receipts; and data/build.json, the commit and build time stamped by npm run build:info. The footer of every page shows that stamp. Opened straight off disk it falls back to the snapshot in scripts/data.js, which npm run sync:fallback regenerates, and says so.

Deploying

The repository is Vercel-ready. vercel.json serves site/ and uses the build step as a guard: it typechecks the engine and runs faucet policy, which throws unless the policy sums to 100%. Headers include a Content-Security-Policy with no inline scripts, and data/ is served uncached so a fresh burn is visible on the next load.

npm i -g vercel
vercel --prod

Not built yet

  • Chain constants. Robinhood Chain's RPC, chain id, router and WETH are read from the environment and left unset in the repository until confirmed against the launch documentation. Nothing is guessed.
  • A scheduler. The engine runs one cycle per invocation. Wiring it to cron or a small runner is deliberately separate from the engine.
  • Claiming rewards from Pons. If Pons requires an explicit claim rather than paying the wallet directly, a source step to call it belongs before plan. The engine treats whatever is in the wallet as spendable.
