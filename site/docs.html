The Faucet

A fee-recycling engine for Robinhood on Pons. It collects the fees a launch throws off, routes every basis point of them back into the project by a fixed policy, and publishes enough for anyone to check that it did.

Two things live in the repository. engine/ is the engine: TypeScript, zero runtime dependencies, a test suite that tries to make it leak. site/ is this website: a static directory with no build step, rendering the files the engine writes.

The claim the site makes is enforced by code. assertPolicyBalanced() throws unless the routing policy allocates exactly 10,000 basis points, and it runs on import, so a leaky policy means nothing starts. assertConserved() throws unless every lamport collected in an epoch either left in a settlement intent or was explicitly carried into the next one.

The cycle

Pons creator vault ─┐
                    ├─→ collect ─→ route ─→ distribute ─→ settle
LP fee vault ───────┘      │         │          │           │
                           │         │          │           └─ intents (unsigned)
                           │         │          └─ Merkle root + claim file
                           │         └─ four buckets, exactly 100%
                           └─ finalized credits inside [fromSlot, toSlot)

An epoch is a half-open slot window. The default is 54,000 slots, about six hours at Solana's 2.5 slots per second. Each stage is a separate module, and the boundaries between them are where the safety properties live.

Sources observe, never move

A fee source reports what it saw. It holds no key and has no way to move money. An adapter bug can produce a wrong number, which the conservation checks downstream will surface, but it can never produce a wrong transfer.

The vault adapter reads each transaction's balance delta on the vault account rather than parsing program logs. When the launchpad ships a new program version, a fee that lands in the vault is still a fee, and the adapter keeps working.

Quiet epochs carry forward

If the collected total is under the settle floor (0.01 SOL), nothing settles. Spending 0.005 SOL in transaction fees to move 0.002 SOL is a net loss, so the whole amount carries forward, and the receipt records it as carried rather than spent. The next epoch picks it up as carryIn.

Routing

Integer division loses remainders. "We lose three lamports an epoch" is exactly the kind of quiet leak this project exists to not have, so allocation uses the largest-remainder method: floor every bucket, then hand the leftover units out one at a time to the buckets with the biggest fractional part.

sum(allocations) === total is guaranteed and asserted. Ties break on the bucket's position in the config, so the same input produces the same allocation on any machine.

BucketShareDestination
Buyback & burn35.00%Market-buys the token; everything bought goes to the burn address.
Holder drip35.00%Split by time-weighted balance; claimed with a Merkle proof.
Liquidity20.00%Added to the pool as protocol-owned liquidity. Not withdrawable.
Build fund10.00%On-chain treasury for tooling, audits, integrations. Spends published per epoch.

The drip

Share of the drip is proportional to balance integrated over the epoch, not the balance at a snapshot block:

weight(owner) = Σ (balance_i × slots_held_i) / total_slots

A snapshot is trivially gamed: borrow a large balance, hold it across the snapshot block, claim, repay. Integrating over the whole epoch makes that attack cost the full epoch rather than one slot.

Holders under the holder floor (1 ROBIN) are not counted, which stops sybil dust from farming the drip. Anything the drip cannot divide evenly is returned as remainder and rolled into the next epoch's collected total. It is never burned by rounding and never quietly retained.

Merkle claims

Claims are hashed into a Merkle tree and the root is published with the claim file. Three details separate a working claim tree from an exploitable one, and each has a test that fails without it.

  1. Domain separation. Leaves hash with a 0x00 prefix, internal nodes with 0x01. Without it a 64-byte "leaf" can be replayed as an internal node and a proof forged for a claim that was never allocated.
  2. No self-pairing. An odd node at a level is promoted, not paired with itself. Duplicating the last node lets one proof validate two different indices.
  3. Index inside the leaf. leaf = sha256(0x00 ‖ u32be(index) ‖ owner ‖ u64be(amount)). A claim contract can mark index n spent in a bitmap and be certain no second leaf shares it.

Internal pairs are hashed in sorted order, so a proof is a flat list of sibling hashes with no left/right bitmap for a verifier to get wrong. The empty tree has a distinct sentinel root, sha256("faucet:empty"), which carries neither prefix and so cannot collide with a real hash.

The site ships its own implementation of this tree in scripts/merkle.js, on WebCrypto, so a holder can rebuild an epoch and check their proof in the browser. The engine's test suite loads that file as-is and asserts identical roots and proofs against the TypeScript implementation, including on the published claim files.

Everything lives in engine/src/config.ts. The site reads a generated copy, so the numbers on the page and the numbers the engine settles with cannot drift apart.

CLI

faucet policy                          show the routing policy and prove it sums to 100%
faucet cycle [--epochs N] [--seed N]   run epochs (mock sources unless --live)
         [--live] [--write-site] [--out DIR]
faucet verify <claims.json> <owner>    verify a published claim proof
faucet doctor                          sanity-check config and RPC

Going live

  1. Mint the token on Pons.
  2. Fill in CONFIG.mint.address and CONFIG.feeAccounts.*.
  3. Copy .env.example to .env and set FAUCET_RPC_URL. Public endpoints rate-limit a full epoch scan; use an authenticated provider.
  4. npm run doctor. Every check must pass. It fails on purpose until the addresses are set, because a live cycle against an unconfigured engine would silently collect nothing.
  5. npm run build && node dist/src/cli.js cycle --live --write-site && npm run sync:fallback

Settlement signing is deliberately not wired to a key. cycle computes and publishes settlement intents; broadcasting them is a separate, explicit step, so a bug in collection can never become a transfer.

Runbook

Reading a receipt

collected is total in, including carry-in. routing lists the four buckets, which must sum to collected. drip gives recipient count, distributed amount, carry-out and the Merkle root. settlement lists the intents; nothing has been broadcast.

Publishing a drip

Publish the claim file where holders can fetch it (the site does this under data/claims/). Fund the claim account with the amount in the fund-merkle intent, which is distribution.total, not the whole drip bucket. The difference is dust that belongs to the next epoch.

When conservation fails

error epoch 4: routed 900 but collected 1000

The engine caught a leak and refused to settle. Nothing was broadcast. Do not retry; capture the inputs and find the bug. assertConserved failing is always an engine defect, never a transient condition.

Changing the split

Edit ROUTING in the config. The basis points must still sum to 10,000 or the engine refuses to import it. Then npm run cycle to regenerate the site data so the page matches what will settle. The change is one commit that changes both.

The site

Static files, no framework, no bundler. It reads data/faucet.json, written by faucet cycle --write-site; data/claims/*.json, the published claim files; and data/build.json, the commit and build time stamped by npm run build:info. The footer of every page shows that stamp, so a deployed page can always be traced to a commit.

Opened straight off disk, where fetch is blocked, the page falls back to the snapshot in scripts/data.js, which npm run sync:fallback regenerates, and says so.

Deploying

The repository is Vercel-ready. vercel.json serves site/ and uses the build step as a guard: it typechecks the engine and runs faucet policy, which throws unless the split sums to 100%. A policy that leaks a basis point cannot be deployed. The headers include a Content-Security-Policy with no inline scripts, and data/ is served uncached so a fresh cycle is visible on the next load.

npm i -g vercel
vercel --prod

npm run serve applies the same headers locally, CSP included, and serves the 404 page for missing routes, so anything that would break in production breaks on localhost:4173 first.

Not built yet

  • Signing. Intents are computed and published; broadcasting is manual by design until the rest is proven.
  • A full holder index. --live reads getTokenLargestAccounts, which caps at 20 accounts. That is a floor for testing; the plan is a streamed balance index feeding the time-weighting.
  • On-chain policy. The split is a committed file today. Moving it on-chain makes changing it cost a visible transaction instead of a commit.
  • A claim front-end. The verifier on the home page derives the proof; submitting it needs a wallet connection and the claim program.
